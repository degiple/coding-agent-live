# 公開（Cloudflare Workers）

公開は人が承認してから行います。承認画面が出たら、人の操作を待ちます。承認を避ける方法は探しません。失敗したときは、推測で直さず、エラーの原文を示して人に知らせます。

## 1. 公開前の確認

1. ローカルで確かめ済みかを確かめる。この会話に、`npx wrangler dev` で動かして確認した記録（何を、どう動かして、どうなったか）があるか見る。無ければ、止めずに登壇者へ「ローカルで確認済みですか」と1問だけ聞く。確認済みと答えたら進み、報告には「登壇者の申告」と書く。まだと答えたら、「先に `npx wrangler dev` で確かめましょう」と伝えて止まる。確認の記録を、こちらで作らない。
2. `wrangler.jsonc` を読み、Durable Objects の `migrations` に `new_sqlite_classes` があるかを確かめる。無ければ、公開せずに人に知らせる（無料プランは SQLite 版だけが使える。`AGENTS.md` の「技術構成」）。
3. 環境変数の有無を、値を表示せずに確かめる。次の形だけを使う。`.env` と `.dev.vars` は開かない・読まない・表示しない。
   - bash: `[ -n "${CLOUDFLARE_API_TOKEN:-}" ] && echo 設定あり || echo 設定なし`（`CLOUDFLARE_ACCOUNT_ID` も同じ）。
   - PowerShell: `if ($env:CLOUDFLARE_API_TOKEN) { '設定あり' } else { '設定なし' }`。
   - `.env` と `.dev.vars` は、あるかどうかだけを `test -f` などで見る。
   - 変数が「設定なし」でも、ここでは止めない。wrangler はログイン済みの認証や `.env` を使うことがあり、この方法では判定できないため。認証に失敗したら、公開の失敗として扱う（4章）。
   - `npx wrangler whoami` は使わない。アカウントの情報が画面に出るため。

## 2. 公開する

1. `npx wrangler deploy` を実行する。オプションで承認を省く指定は付けない。
2. 承認画面（許可の確認）が出たら、内容を人が読んでから許可する。許可されなければ、公開しないで止まる。
3. 出力を残す。伏せる対象はアカウントID・トークンらしい文字列だけで、あればその部分だけ伏せて残し、伏せたことを明示する。公開URLとバージョンIDは伏せない（`wrangler whoami` を使わないのと同じ理由で、アカウントの情報を画面や記録に出さないため）。次の章で、出力に表示された URL を使う。
4. Codex で動かす場合、公開（`npx wrangler deploy`）と、次の章の接続確認（`curl`）にネットワークの承認を求めてよい。承認画面が出たら、人の操作を待つ。

## 3. 公開した URL に接続する

1. URL は `wrangler deploy` の出力に表示されたものだけを使う（形は `https://<名前>.<サブドメイン>.workers.dev`）。推測で組み立てない。表示されなければ、そう報告して止まる。
2. `curl -sS -m 15 -o /dev/null -w '%{http_code}\n' <URL>` で応答を確かめる。続けて `curl -sS -m 15 <URL> | head -n 20` で、返ってきた画面の先頭を見る。
3. 公開の直後は接続できないことがある。失敗したら、数秒おいて最大3回まで同じコマンドを繰り返す。3回とも失敗したら、各回の出力をそのまま報告する。
4. 状態を取る API（読むだけの GET）があれば、1回だけ呼んで応答の形を確かめてよい。書き込みを伴う操作（POST など）は、本番の状態を汚すので行わない。

## 4. 失敗したとき

ログインの期限切れ、workers.dev のサブドメイン未登録、権限の不足、ビルドエラーなどで失敗することがある。次の順で対応する。

1. エラーの原文を、先にそのまま引用して示す（英語は英語のまま）。伏せる対象はアカウントID・トークンらしい文字列だけで、あればその部分だけ伏せ、「伏せた」と明示する。公開URLとバージョンIDを含め、それ以外は原文のままにする。
2. 次に、人に何をしてほしいかを短く書く。原因は推測で断定しない。原文に無い理由を足さない。
3. アカウント・権限の問題（ログインの期限切れ、サブドメイン未登録、権限の不足、プランなど）は、自分では直さない。`wrangler login`、`wrangler secret put`、プランの変更、トークンの作成や貼り付けはしない。人の操作が必要なものとして知らせる。
4. コードや設定の誤り（ビルドエラーなど）は、エラーの原文を示して修正案を出し、登壇者の許可を得てから直す。許可なく直さない。直したら、ローカルでの確認（1章の1）をやり直してから、「2. 公開する」に進む。
5. 3の問題について、人が対処したと伝えてきたら、「2. 公開する」からやり直す。

## 5. 報告する

結果は、次の2つに分けて書く。

- 確かめたこと: 何を、どのコマンドで、どうなったか。例: `npx wrangler deploy` が成功し URL が表示された。`curl` の応答が 200 だった。
- 確かめていないこと: 例: 複数のブラウザで互いに書き込みが反映されるか、携帯の画面、再公開後の状態の保持、同時に多数が開いたときの負荷。人が URL を開いて確かめる項目として挙げる。

公開した URL も書く。確かめていないことを「たぶん動く」と書かない。
