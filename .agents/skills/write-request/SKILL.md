# 依頼文づくり

このスキルは `docs/request.md` を作る・更新するだけです。コードは書きません。実装は、登壇者が計画を確認してから別に頼みます。

## 場面を決める

- 場面A（素の版）: アプリ名だけが渡された。または `docs/request.md` がまだ無い。
- 場面B（見た目の仕上げ）: 見た目の投票結果が渡され、`docs/request.md` がある。見た目の結果が渡されたのに `docs/request.md` が無いときは、先に場面Aを実行して `docs/request.md` を作り、そのあとで場面Bに進む。この連鎖のときは、場面Aの最後の案内（計画モードで渡してください）と全文表示を省き、場面Bの表示で代える。
- どちらか判断できないときは、登壇者に「依頼文を新しく作りますか、見た目を足しますか」と1問だけ聞く。

## 場面A: 素の版の依頼文を作る

1. アプリ名を確かめる。候補は「みんなでクリック」「ワードクラウド」「共同ドット絵」「コメント流し」の4つ。渡されていなければ、どれかを1問だけ聞く。ここでは見た目も仕様も聞かない。
2. `references/apps.md` の該当アプリの節を読む。`AGENTS.md` の「技術構成」と「守ること」も読む。読んだ内容を、下の雛形に写す。apps.md の該当アプリの節にある全項目（画面・操作・保存・制限・確認・更新の仕組み・作らないもの）を、「暫定」「過去の記録」の印も含めて、依頼文のどこかに写す。落とした項目が無いか、書いたあとに節と見比べる。
3. 雛形どおりに `docs/request.md` を書く。`docs/` が無ければ作る。すでにあるファイルは上書きしてよいか登壇者に確かめる。
4. 書いた依頼文の全文を画面に表示する。最後に「実装はまだ始めていません。計画モードで、この依頼文を渡してください」と伝える。

### 雛形

```markdown
# 依頼文: <アプリ名>

## Goal

<アプリ名>を作る。<apps.md の「画面」「操作」を2〜3文で>。視聴者がログインなしで同時に開いて書き込め、全員の画面に反映される。

## Context

- 技術構成は AGENTS.md の「技術構成」に従う。要点: Cloudflare Workers、全員で共有する状態は Durable Objects（SQLite 版。`wrangler.jsonc` の `migrations` に `new_sqlite_classes`）、画面は素のHTML・CSS・JavaScript（`public/`）、サーバーは `src/`、画面の更新は2秒ごとのポーリング。
- 基本仕様:
  - <apps.md の「保存」「制限」「更新の仕組み」を、そのアプリの分だけ写す。印（暫定・過去の記録）も残す>
- Cloudflare の仕様で分からないことは、推測で書かず、先に MCP の `cloudflare-docs` で調べる。

## Constraints

- 見た目は素のままにする。色・書体・演出・口調は付けない。見た目は投票で後から決める。
- <apps.md の「作らないもの」を写す。ドット絵のときは「基本仕様だけを作り、独自の工夫は足さない」も書く>
- 送信の間隔を制限し、入力の長さを制限する。値は基本仕様に従う。
- 実在の個人名・メールアドレス・会社名をコードにもサンプルにも書かない。秘密情報を書かない。`.env` と `.dev.vars` を読まない。
- 実装の前に計画を出し、人が確認するまで待つ。公開（`wrangler deploy`）はしない。

## Done when

- `npx wrangler dev` で起動でき、2つのブラウザで開いて、片方の書き込みがもう片方に数秒以内に反映される。
- <apps.md の「保存」に合わせた確認。保存するアプリは「`wrangler dev` を再起動しても状態が残る」。コメント流しは省き、代わりに「`wrangler dev` を再起動したあとも、開いたままの画面が新しいコメントを受け取れる」を入れる。apps.md に「確認」の項目があるアプリ（共同ドット絵）は、その確認も入れる>
- 範囲外や不正な値を直接送っても、サーバーが拒否して状態が壊れない。
- 完了の報告に、確かめたこと（何を、どう動かして、どうなったか）と、確かめていないことを分けて書く。
```

## 場面B: 見た目の仕上げを依頼文に足す

入力は投票の3結果です。

- 2-1 見た目のテーマ（例: レトロゲーム風／和風／ネオン／ハロウィン）
- 2-2 キャラクターの口調（例: 執事／戦国武将／ギャル／ロボット）
- 2-3 送信時の反応（例: 花火が上がる／絵文字が飛び出す／キャラクターがひと言しゃべる／送った人の書き込みが光る）

渡されていない結果があれば、その確認も下の「聞き取り」の3問に含める（別枠で増やさない）。渡された投票結果そのものはAIが聞き直さない。

### 聞き取り（この場面だけ）

1. 聞くのは、投票結果の具体化と、渡されていない結果の確認だけ。渡された結果を選び直させる質問はしない。書体は聞かない（追記する節の「書体」の行で決める）。
2. 質問は最大3問。欠けた結果の確認もこの3問に含める。3結果それぞれについて、実装に効く点を1つずつ選ぶ。すでに決まっていて聞く必要のないものは省き、質問を減らす。たとえば次のようなものです。
   - テーマ: 主役にする色の方向（例: ネオンなら青系かピンク系か）。
   - キャラクター: 画面での呼びかけ方（例: 執事なら「お嬢様」か「ご主人様」か）。
   - 送信時の反応: 出る場所と強さ（例: 花火なら送信ボタンの近くか画面全体か）。
3. 各質問の選択肢は「おまかせ」を含めて2〜4個にする。先頭に推奨を置き、最後に「おまかせ」を置く。欠けた投票結果を確認する質問は、候補を3つに絞って「おまかせ」を足す（計4個で、この規定に収まる）。
4. 質問の出し方:
   - 選択肢つきで質問できるツール（Claude Code の AskUserQuestion など）が使えるときは、それを使う。1回で3問まとめてよい。
   - 使えないときは、通常の文章で1問ずつ聞く。選択肢に番号を振って書き、登壇者の返事を待ってから次の質問に進む。返事が番号でも言葉でも受け取る。
5. 答えが返ってこない問いは、推奨（先頭の選択肢）で進め、その旨を追記に書く。曖昧な返事（どの選択肢とも取れない、複数に取れる）にも聞き返さず、推奨で進めて、その旨を追記に書く。

### Constraints に追記する

1. `docs/request.md` を読み直す。「Constraints」の末尾に、次の節を追加する。同じ節がすでにあるときは、重複させず中身を置き換える。
2. 既存の Constraints の行は変えない。「見た目は素のままにする」の行だけは、追記した節と食い違うので、「見た目は下の『見た目の仕上げ』に従う」に書き換える。
3. 追記する節の形:

```markdown
### 見た目の仕上げ（投票で決定）

- テーマ: <2-1の結果>。<聞き取りの答え>
- キャラクター: <2-2の結果>。画面の文言（見出し・ボタン・案内・エラー）をこの口調にする。<聞き取りの答え>
- 送信時の反応: <2-3の結果>。<聞き取りの答え>
- 書体: テーマに合わせて選ぶ。日本語が崩れないこと。外部のWebフォントを使う場合は1つまでにし、読み込めなくても読める代替フォントを指定する。
- 見た目だけを変える。仕様・保存・送信の制限は変えない。送られた文字をHTMLとして解釈しない。
- 仕上げのあとも、Done when の確認がすべて通ること。
- 計画: この修正では計画の確認は不要（計画モードは最初の1回だけ）。Constraints の「実装の前に計画を出し、人が確認するまで待つ」は、この修正には適用しない。公開（`wrangler deploy`）はしない。
```

### 2-2と2-3の連動

2-3が「キャラクターがひと言しゃべる」のときは、2-2のキャラクターの口調でしゃべる。節の「送信時の反応」の行に次を加える。「送信するたびに、短いひと言を<キャラクター>の口調で画面に出す。ひと言は数種類を用意し、順番に変える」。2-3がそれ以外のときは、反応の演出とキャラクターの口調は別のものとして書く。

### 表示して終わる

追記した節の全文と、書き換えた1行を、変更点として画面に表示する。追記と、「見た目は素のままにする」1行の書き換えが差分になる。`docs/request.md` が git の管理下にあれば、`git diff docs/request.md` の出力も見せる。最後に、次の一手として「docs/request.md の『見た目の仕上げ』を反映して、素の版を直してください」と伝える。このスキルでは直さない。

## 守ること

- 依頼文の形は Goal・Context・Constraints・Done when の4要素に固定する。要素を増やさない。
- `references/apps.md` に無い仕様を足さない。値が「暫定」「過去の記録」のものは、そのまま写して由来を残す。
- 実在の個人名・会社名・メールアドレスを書かない。ダミーを使う。
